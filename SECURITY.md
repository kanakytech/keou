# Security

## Reporting a vulnerability

Email **kevyn@kanaky.xyz** with `SECURITY` in the subject. Please do not open a public
issue for anything exploitable.

Include what you did, what happened, and what you expected. A reproduction — even a
rough one — is worth more than a description. You will get a first reply within 72
hours, and credit in the fix commit unless you would rather not be named.

There is no bounty. This is a solo project.

## What is in scope

The code in this repository, and the hosted instance at `studio.kanaky.xyz`.

Out of scope: findings that require an attacker to already hold valid credentials for
the account they are attacking, rate-limit tuning on a self-hosted instance you control,
and reports generated by a scanner without a working reproduction.

## Things worth knowing before you look

**Bring-your-own-key.** Provider keys live in the visitor's browser and ride each
request in an `X-Provider-Key` header. They are never written to disk, database or
logs. If you find a path where one is persisted or logged, that is a real finding —
please report it.

**Self-hosted instances need a seeded account.** `ADMIN_EMAIL` / `ADMIN_PASSWORD` seed
the first account; public self-serve signup is off by default outside the hosted
community edition. An instance deployed without them has no way to sign in — that is
intended, not a lockout bug.

**The anonymous surface.** `/api/essai/*` is reachable without authentication in the
hosted community edition only. It is rate-limited per IP and its outputs are watermarked
and public by design. It is the largest unauthenticated surface in the codebase and the
first place worth looking.

## Past findings

The synthetic-session bootstrap that used to hand every visitor a session in the
`opensource` edition was removed before the first public release. It is documented in
`src/routes/auth.js` so nobody reintroduces it.
